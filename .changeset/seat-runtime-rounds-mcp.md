Add `runRounds` and `mcpToolkit` to `@homeflare/seat-runtime`. `runRounds({ chat, toolkit, maxRounds, onRound })` is the one round loop the seats share: model turn, tool results, model turn, until the model asks for no tools or `maxRounds` tool rounds have run, and then ONE more turn with no toolkit and `toolChoice: 'none'` so a run ends in an answer (`capped` says the cap fired). A provider that still asks for a tool on that forced turn (`AiError` reason `ToolNotFoundError`, which is what `SeatModel`'s compat provider raises, or `InvalidOutputError` from the SDK's own decode) does not fail the run: the result is `capped` and `unanswered`, its `response` is the last tool round's, and `seat_rounds_unanswered_total` counts it (any other failure of the forced turn still fails the run). `maxRounds` must be a positive integer or the run dies with a `RangeError` before any model call. Every turn is a `seat.round` span, counted in `seat_rounds_total` and `seat_rounds_capped_total`. `mcpToolkit(url, headers)` connects the official `@modelcontextprotocol/sdk` client (exact `1.31.0`, a new pinned dependency) over Streamable HTTP and returns the server's tools as a ready-to-run Effect AI toolkit (each a `Tool.dynamic` carrying the server's own JSON Schema) plus `listResources` and `readResource`. A tool failure (`isError`, a JSON-RPC error, a dropped call) is returned to the model as the tool's result, with any echoed query value or header value redacted from its text (a successful result is delivered verbatim); connecting and listing fail with `McpToolkitError`, whose message and `cause` never hold the headers or the query string, nor a query value or header value (6 characters and up) that the server echoes back on its own (a value the server transforms is not caught). The cause is a scrubbed copy of what the SDK threw: name, message, stack and `code`, so `cause instanceof McpError` does not hold; a refused fetch's own `path` field is the full URL under Bun. Results are text: image, audio and blob blocks become one-line markers. `@effect/ai-openai-compat` rc.115 cannot decode a tool call for a `Tool.dynamic` alone (fixed in rc.118), so an argument the server's schema does not declare is dropped until the pin moves. An explicit `null` on an optional argument is delivered to the server as `null`, not deleted. `mcpToolkit`'s `connectTimeoutMs` option (default 15 000 ms; a finite number above 0 and at most 2 ** 31 - 1, or a `RangeError` defect) bounds the WHOLE handshake, `initialize` and the `notifications/initialized` that follows it (the SDK bounds only the first), and each `tools/list` page read at startup, per request and not as a total; `listResources`, `readResource` and tool calls keep the SDK's 60 s. The handshake is interruptible, so a caller's `Effect.timeout` or a shutdown ends it too, and a failed or interrupted `mcpToolkit` leaves nothing in the caller's scope, whether it fails in the handshake or in the `tools/list` after it (the client's finalizer is registered only once the whole toolkit is built), so `Effect.retry` around `mcpToolkit` does not accumulate clients, sessions or sockets.
